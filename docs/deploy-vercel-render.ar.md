# النشر على Vercel وRender مع Neon أو Supabase

الهدف: الواجهة العامة على Vercel، والـAPI وعامل Telegram على Render، وقاعدة
PostgreSQL دائمة على Neon أو Supabase. لا ينشئ `render.yaml` قاعدة بيانات على Render.
هذه ملفات جاهزية للنشر؛ وجودها في GitHub لا يعني أن الخدمات نُشرت بالفعل.

## 1. قاعدة البيانات

الاختيار المقترح هو **Neon PostgreSQL**. أنشئ مشروعًا من [Neon](https://console.neon.tech)
في منطقة قريبة من منطقة خدمات Render، ثم انسخ رابط PostgreSQL من Connect إلى
مدير كلمات المرور مؤقتًا. استخدم رابط **Direct / غير pooled** لهذا الإعداد؛
سيستخدمه التطبيق والعامل وترحيلات Alembic. احتفظ بخيارات TLS مثل `sslmode=require`.
لا ترسل الرابط في المحادثة ولا تضعه في Git أو إعدادات Vercel العامة.

إن اخترت **Supabase** بدلًا منه، استخدم رابط PostgreSQL من Connect، وليس
`SUPABASE_URL` أو مفاتيح anon/publishable. استخدم الاتصال المباشر إن كان متاحًا
من Render، أو **Session pooler على المنفذ 5432** عند الحاجة إلى IPv4؛ تجنّب
Transaction pooler على 6543 في هذا الإعداد. لا نستخدم Supabase Auth؛ حسابات
المشروع الحالية تبقى مسؤولة عن الدعوات والجلسات والصلاحيات.

يدعم التطبيق روابط `postgres://` و`postgresql://` عبر تحويل اسم المشغّل إلى
`postgresql+psycopg://` دون تغيير المستخدم أو كلمة المرور أو خيارات TLS.
ابدأ بقاعدة جديدة لهذا المشروع. إذا كانت تحتوي بيانات سابقة، خذ نسخة احتياطية
وافحص صندوق الإرسال قبل تشغيل أي عامل إرسال. راجع حدود وتكلفة وحفظ النسخ
الاحتياطية لخطة Neon/Supabase المختارة؛ اعتماد البرنامج لا يوفّر نسخة احتياطية.

## 2. إنشاء بوت Telegram

من الحساب الموثّق [@BotFather](https://t.me/BotFather)، أرسل `/newbot` واختر
اسمًا واسم مستخدم ينتهي بـ `bot`. احفظ الـToken لإدخاله في Render فقط، وأرسل
اسم المستخدم للمساعدة في الربط. لا تضفه إلى Vercel أو ملفات المستودع.

## 3. ربط GitHub بـRender

1. افتح [Render Dashboard](https://dashboard.render.com/) واختر **New → Blueprint**.
2. اربط حساب GitHub وامنح Render وصولًا إلى `MohammedTeir/halal-quant`، ثم اختر
   المستودع وفرع `main` والملف `render.yaml`.
3. راجع الخدمتين قبل إنشائهما: `halal-quant-api` و`halal-quant-telegram`.
   الملف يحدد خطة **starter المدفوعة** لكل خدمة، لأن تشغيل العامل الدائم
   وترحيلات ما قبل النشر يتطلبان خطة مناسبة. راجع السعر المعروض في حسابك؛
   لا يُنشئ رفع الملفات وحده أي اشتراك.
4. أدخل `DATABASE_URL` كرابط Neon/Supabase السري في خدمة API، و
   `TELEGRAM_BOT_TOKEN` في العامل عندما يطلبهما Render. العامل يشير إلى نفس
   `DATABASE_URL` من خدمة API، فلا تنشئ له قاعدة مستقلة.
5. عند النشر، تُثبّت الاعتماديات من `uv.lock`، وتنفّذ خدمة API
   `.venv/bin/alembic upgrade head` قبل بدء التشغيل. لا تشغّل ترحيلات متزامنة
   من العامل. إذا سبق تشغيل العامل اكتمال أول ترحيل، أعد تشغيله بعد جاهزية API.
6. انتظر نجاح `/health/ready` واحفظ عنوان API الفعلي الذي يعرضه Render، مثل
   `https://your-api.onrender.com`. أرسل **هذا الرابط العام فقط** في المحادثة.

الاعتماديات الأصلية للبروكر وGemini غير مفعّلة في هذا الإعداد. لا تنسخ أسرار
بيئة التطوير إلى الاستضافة تلقائيًا. لا يوجد مفتاح لوحة مشترك افتراضيًا؛
دخول المستخدمين بالحسابات والدعوات.

## 4. تحديد عنوان Render وربط Vercel

ملف `vercel.json` يشير مبدئيًا إلى نطاق `.invalid` متعمد، حتى لا يرسل بيانات
الدخول إلى خادم آخر قبل معرفة عنوان خدمة Render الخاصة بك. بعد إنشائها ننفذ:

```sh
node scripts/configure_vercel_api.mjs https://YOUR-API.onrender.com
```

الأمر يقبل عنوان HTTPS على `onrender.com` فقط، دون كلمة مرور أو مسار أو query،
ويحدث وجهتي `/api/v1/*` و`/health/*` في `vercel.json`. احفظ هذا التغيير في
`main` قبل نشر Vercel. في التعاون عبر المحادثة، يكفي إرسال رابط Render العام
لأقوم بتحديثه واختباره ورفعه إلى GitHub.

بعد ضبطه:

1. افتح [Vercel New Project](https://vercel.com/new)، واربط GitHub، ثم **Import**
   للمستودع نفسه `MohammedTeir/halal-quant`، دون إنشاء نسخة أو مستودع آخر.
2. استخدم Root Directory = جذر المستودع، وFramework Preset = **Other**.
   إعدادات المستودع تحدد Build Command = `node scripts/build_dashboard.mjs`
   وOutput Directory = `dist`. لا يحتاج هذا البناء تثبيت حزم npm.
3. لا تضف قاعدة البيانات أو رمز البوت أو مفاتيح البروكر إلى Vercel.
4. انشر فرع `main` واحفظ رابط الموقع الفعلي. أرسله في المحادثة.
5. في Render → خدمة API → Environment، اضبط `PUBLIC_BASE_URL` إلى رابط
   Vercel الثابت بـHTTPS، دون مسار، واترك `SESSION_COOKIE_SECURE=true`، ثم
   أعد نشر الخدمة لتطبيق المتغير.

الواجهة وطلبات API تظهر للمتصفح من أصل Vercel نفسه بفضل external rewrites.
ملف جلسة HttpOnly لا يحدد Domain، فيرتبط بعنوان Vercel الذي استقبل منه المتصفح
الرد. لا نفتح CORS ولا نحفظ مفاتيح الدخول في localStorage. يجب التحقق من مرور
`Set-Cookie` وطلبات CSRF على النشر الحقيقي؛ اختبارات المتصفح المحلية لا تثبت
سلوك وسيط الاستضافة. استخدم رابط Vercel الثابت نفسه للدخول؛ روابط المعاينة
المختلفة تملك جلسات مختلفة.

## 5. إنشاء المسؤول وربط البوت

من Render Shell الخاص بخدمة API:

```sh
.venv/bin/python -m services.accounts.cli YOUR_ADMIN_EMAIL
```

افتح رابط التعيين الذي يظهر **بشكل خاص**، وحدد كلمة المرور ثم سجّل الدخول من
Vercel. لا تنشر مخرجات هذا الأمر؛ الرابط اعتماد مؤقت يستخدم مرة واحدة.
إذا لم تكن `PUBLIC_BASE_URL` مضبوطة بعد، اضبطها قبل تنفيذ الأمر.

من **Account & Telegram** أنشئ رمز ربط، وأرسل `/link CODE` إلى البوت في الخاص
أو في مجموعة تكون أنت والبوت مسؤولين فيها. أبقِ الوجهة معطلة حتى نحدد رسالة
القبول الفعلية. لا تشغّل webhook أو عامل polling آخر للبوت نفسه.

## 6. قبول النشر الفعلي

نراجع بعد توفير روابط الخدمات وإعداد الأسرار في لوحاتها:

- جاهزية قاعدة البيانات والترحيل `0007_access_delivery` من خدمة API.
- HTTPS، وإعداد المسؤول، وتسجيل الدخول عبر Vercel وملف الجلسة وCSRF.
- استمرار الجلسة بعد إعادة التحميل، وإلغاؤها عند الخروج أو تغيير كلمة المرور.
- إنشاء مستخدم بالدعوة وعزل الأدوار، والإنجليزية افتراضيًا والعربية/RTL.
- توثيق وجهة Telegram الخاصة أو المجموعة، ثم اختيار نوع التنبيه واللغة.
- **بعد تحديد الوجهة وموافقتك على رسالة قبول واحدة:** تفعيل الوجهة وإنتاج
  حدث بحثي معلوم، والتحقق من حالة `SENT` ومعرّف الرسالة ورؤيتها في Telegram.
  لن ننتج إشارات أو نفعّل kill switch في بياناتك الفعلية فقط لإرسال تجربة.
  نختار وسيلة تحقق منفصلة أو حدثًا معتمدًا قبل الإرسال.
- حفظ دليل النشر دون أسرار، مع إبقاء `UNCERTAIN` دون إعادة تلقائية.

إلى أن تُنفّذ هذه الخطوات، قبول النشر في المرحلة السابعة **معلّق**. لا تتغيّر
متطلبات قبول المراحل السابقة ولا تُفعّل أوامر تداول حقيقية.

تم التحقق محليًا من **522 اختبار Python** واختبارَي بناء وإعداد مسارات Vercel،
وفحص ملفات الإعداد مقابل مخططات المنصتين الرسمية. راجع
[تقرير جاهزية الاستضافة](../reports/milestone7-hosting-readiness-2026-10-30.json).
هذه الاختبارات لا تستبدل التحقق من النشر الفعلي والجلسات والتسليم.
